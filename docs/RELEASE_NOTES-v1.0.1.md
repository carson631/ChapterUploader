# ChapterUploader v1.0.1

配套「阅文·作家助手」（Electron 客户端）的章节批量上传 / 草稿校对工具。通过 DevTools 协议（CDP）
直接操作客户端页面，不用模拟鼠标坐标，也不改动客户端本体（只加一个调试端口开关，可随时还原）。

## 这个版本改了什么

**一句话：把流水线里的「死等」换成「条件等待」，每章快约 10 秒；启动时间不变（本来也没有水分）。**

| 环节 | 1.0.0 | 1.0.1 | 省 |
|---|---|---|---|
| 点「新建章」→ 写标题 | 1600 + 1000 ms 固定等待 | 新章出现即写（典型 ~0.35 s） | 2.2 s |
| 写完正文 → 校验 | 1500 ms | 字数到位即校验（~0.55 s） | 0.95 s |
| 打开校对面板 → 读状态 | 900 ms | 检测按钮渲染出来即读（~0.28 s） | 0.6 s |
| 点「检测」→ 开始查状态 | 3500 ms × 2 块 | 一进入「检测中」即查（~0.3 s × 2） | 6.4 s |
| 面板就绪 → 点检测 | 400 ms | 200 ms | 0.2 s |

- 新增 `waitThen()`：120 ms 一轮探测，页面就绪立刻走；**到原来那个时长点无条件继续**，
  所以最坏情况与 1.0.0 完全一致，只可能更快
- 轮询间隔减半：草稿加载判定 700→300 ms（连判 2→3 次）、章节切换确认 400→200 ms、检测状态 1000→500 ms
- 「新建章是否真的建出来」用「路由 hash 变了 / 侧栏条目数涨了 + 标题框已空或已是本章」判断，
  不会提前把标题写进上一章；「内容未保存，是否继续」弹窗照旧自动点掉，每章只点一次
- 日志区不再拖慢界面：改批量刷新（120 ms 一批）、关掉撤销栈、上限 4000 行

**实测对比**（同环境、交替启动各 8 轮、去掉前两轮冷启动）

| 项 | 1.0.0 | 1.0.1 |
|---|---|---|
| 启动到主窗口出现（中位数） | 648.4 ms | 647.6 ms |
| 每章耗时（上传 + 校对） | — | **省 ≈10.4 s** |
| 每章耗时（草稿校对） | — | **省 ≈7.7 s** |

启动差异在噪声内（±1 ms）：本版没有改启动路径，Fusion + 读 QSS + 建界面已是最短路径。

## 这个版本能做什么

**上传新章**
- 从本地分章 txt 目录（`第243章 243五虎加冠.txt`）逐章：新建章 → 写标题 → 贴正文 → 字数校验 → 校对 → 下一章
- 章节区间、标题格式（`第243章 243五虎加冠` / `第243章 五虎加冠`）、收尾动作（不点 / 保存 / 发布）都可配
- 断点续跑：有进度记录时自动从上次的下一章开始
- 同号章节已存在时按「字数 > 0」判重；只有编号、0 字的空占位章会在原章里填充，不新建

**校对已有草稿**
- 不动标题正文，只把客户端里已有的章节逐章切过去，跑「错别字 → 病句」检测，把建议逐条改掉
- 切章走客户端内部的完整目录（`chapterStore`）＋路由跳转，**不受分卷收起、虚拟列表只渲染十几条的限制**
- 实测第 151 / 300 / 700 / 1200 章均在 15~300 ms 内命中

**校对链**
- 一块检测完就立刻改这一块（改字会改变下一块的结果）
- 滚到红线 → 派发 `mouseover` 唤出修改框 → 点框里的蓝字建议 → 复核红线少一条
- 改不动的不死等：没有建议就按 `data-correct-word` 直接替换，连替换都不行就点「忽略」

| 文件 | 说明 |
|---|---|
| `ChapterUploader-v1.0.1-win64-portable.zip` | **推荐**。解压即用，已带 Qt 运行库；双击 `ChapterUploader.exe` |

运行环境：Windows 10/11 x64，客户端「阅文·作家助手」已安装（默认 `D:\AppStoreSoftstore\Install\YuewenEdit`）。

## 上手三步

1. 打开程序 → 「开启调试端口」（会改写客户端一个入口文件，原文件自动备份为 `package.json.ywbak`，界面上「还原客户端」可随时恢复）
2. 重启客户端，点「连接」（默认 `127.0.0.1:9222`）
3. 左栏选模式 → 选作品 → 填章节区间 → 开始

详细说明见仓库 [README.md](https://github.com/carson631/ChapterUploader#readme)。

## 已知边界

- 依赖客户端 DOM 与内部 Pinia store，客户端大版本升级后选择器可能要跟着改（选择器全在 `js/site.js`，改完不用重编译）
- 校对是 AI 服务，逐条自动替换会连误判一起改：重要章节建议先跑一章，或把「收尾动作」设成不点按钮，人工扫一眼再发
- 串行执行，一章约 10~50 秒（主要耗在校对检测，这段时间是服务端 AI 算的，程序侧无法压缩）
- 客户端窗口保持前台可见时最快；被完全遮挡时 Electron 会把页面定时器限流到 1 秒，等待会变长
